## Context

见 `proposal.md`。当前 `develop` 保留官方候选祖先，但候选在原 `V1.9.1_2` 末尾增加索引，使旧库记录的 checksum 与资源文件不一致。现有治理脚本会无条件拒绝相对官方基线修改历史 SQL，因此兼容修复还需要一个内容精确、默认关闭的例外机制。

## Goals / Non-Goals

**Goals:**

- 让旧官方基线数据库无需 `repair` 即可升级。
- 让空数据库和旧库最终得到相同的索引及 Migration 历史。
- 让 CI 只能接受这一次、这一文件、这一组确定内容摘要的历史脚本恢复。
- 在任何真实数据库变更前识别 checksum 状态并形成可审计的验证证据。

**Non-Goals:**

- 本变更不直接升级本地常驻库、服务器库或生产库。
- 不自动修复已经用候选改写脚本初始化的数据库。
- 不引入通用 Migration 重写机制，也不更改 Flyway 配置以忽略校验错误。

## Decisions

### 恢复旧内容并新增补偿 Migration

从旧官方基线 `11ddfef84c49fce62bc4847d21df618b2b213964` 恢复 `V1.9.1_2` 的精确字节内容，将索引 DDL 放入 `1.9.1` 目录下的高序号本地补偿版本。高序号降低同一官方补丁版本内的命名碰撞，同时仍排在未来更高产品版本之前。

替代方案是保留改写脚本并对旧库执行 `repair`。该方案会把实际执行内容与 schema history 声明的 checksum 混同，也会把危险操作推给每个环境，因此不采用。

### 新 Migration 对既有索引安全

补偿脚本先依据当前 schema 和索引列定义判断目标索引是否存在，仅在缺失时创建；若同名索引结构不符合预期则失败，避免把异常状态伪装成成功。这样可处理人工预建了正确索引的旧库，但不会掩盖结构冲突。

### 使用摘要锁定单一治理例外

新增机器可读的 Migration 兼容例外清单。每项必须包含仓库相对路径、当前官方基线内容 SHA-256、允许恢复内容 SHA-256 和原因。治理脚本先验证官方基线 blob 摘要，再验证工作树目标摘要；只跳过这一条历史文件的 M/D 禁令，其余版本唯一性、顺序及目录规则继续执行。

替代方案是把路径加入普通 allowlist。普通路径级允许无法阻止该文件再次被任意改写，约束不足。

### 真实升级前执行只读预检

升级说明提供只读 SQL，确认 schema history 中 `V1.9.1.2` 的 checksum、成功状态和目标索引定义。旧 checksum 进入标准升级；候选新 checksum 或未知值立即停止。工具不得自动执行 `repair`。

## Risks / Trade-offs

- [未来上游也新增同版本号] → 使用保留的高序号并由基线检查检测版本重复；后续上游同步发现冲突时，在尚未部署前另行调整。
- [候选版本创建的数据库无法直接校验恢复后的脚本] → 预检明确识别并停止；只有在备份和专项验证后才允许人工规范化。
- [条件 DDL 掩盖错误索引] → 只接受名称和列定义均符合预期的索引，其他情况显式失败。
- [历史脚本恢复仍属于官方文件补丁] → 在 `UPSTREAM_MODIFICATIONS.md` 和精确摘要清单中登记，可在上游正式修复后评估移除。

## Migration Plan

1. 在功能分支恢复历史脚本并新增补偿 Migration，运行治理单元测试和 OpenSpec 严格校验。
2. 从旧基线 SHA 创建隔离数据库并迁移到旧状态，再切换到修复版本执行 validate/migrate，核对 checksum、Migration 记录和索引。
3. 对空隔离数据库执行修复版本全量迁移并核对相同结果。
4. 合并到 `develop` 后，仅对明确选定且已备份的开发数据库运行只读预检；符合旧 checksum 才执行升级。
5. 若应用层需要回滚，可回退应用版本；已创建索引默认保留。只有确认性能或兼容问题时，才以新的回滚 Migration 删除索引，不改写历史或直接回退 schema history。
